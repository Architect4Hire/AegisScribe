AegisScribe Armory — design reference

The visual system for the character armory, and the four screens that define it. This page is the source of truth for anything visual in src/web/: tokens are copied from here, not invented, and a component that disagrees with this page is the thing that is wrong.

Status v2 — multi-tenant Theme Dark only, by decision Data shown Fictional characters, real ID conventions Skill .claude/skills/aegisscribe-design-system
Read this before building anything. Three things on this page are not aesthetic preferences and cannot be dropped in implementation: the Blizzard attribution in the app footer, the generated-content label and stop control on every AI surface, and the interpreted-filter chip row above natural-language results. Each one discharges an obligation in CLAUDE.md → Restrictions. They are drawn here so nobody has to remember them.
01

Colour

Foundations

The item-quality palette already owns green, blue, purple and orange, and an experienced player reads gear by colour before reading any text. So the interface itself is near-monochrome: cold gunmetal surfaces, one brass accent, and semantic colours held to muted, cooler values. The only saturated colour on an AegisScribe screen is data. If a new UI element wants its own hue, the answer is no.

The item cell

Most-repeated object

Everything in this app eventually renders an item, so this cell is worth getting exactly right. Icon, name, sub-line, item level — always in that order, always the same widths, so a rail of sixteen reads as one column and the eye can scan the right edge for the weak slot.

The flagged cell tints its background and adds a word. It does not repaint the left border — that border is item quality, and letting a semantic state borrow it would make an uncommon belt look legendary.

The item cell is the Wowhead integration. It renders an outbound link built from the Blizzard item ID; Wowhead's own script attaches the tooltip on hover. The server never contacts Wowhead — see .claude/rules/external.md. Set renameLinks:false in the tooltip config or the script overwrites these names.
07

App chrome & tenant context

Multi-tenancy

AegisScribe is multi-tenant, and the single most important job of the chrome is making the active community obvious at all times. A user who is an officer in one guild and a plain member in another will otherwise take an officer action in the wrong place — and the app will correctly let them, because they really are an officer somewhere.

/t/ashes-of-dawn/*Header — every tenant route
AEGISSCRIBE
Roster Calendar Armory Advisor

The switcher shows the community and the viewer's role in it. Opening it lists every community they belong to; picking one navigates — it never mutates hidden state, because a stored "current tenant" and the URL will drift, and when they do the user is looking at one community's data inside another's chrome.

The tenant lives in the route. /t/:tenantSlug/..., mirroring the API. Services build request URLs from the active route, never from a variable. A tenant guard confirms membership before the route activates, and a 404 means "not yours" — route to the picker, never render an error, and never let the UI distinguish "doesn't exist" from "not a member", because the API deliberately doesn't either.

Including the ones people skip

Guild roster & natural-language query

The interpreted filter

The chip row under the query box is the most important element on this screen. The model turns plain English into a constrained filter object; the chips are that object, rendered. A user who sees “ilvl > 620” when they meant 640 spots it in one read and fixes it by editing a chip — instead of trusting a wrong answer that looks authoritative.

Crafting & gear advisor

Grounded chat

The advisor answers from retrieved context — this character's gear and the recipe catalogue — and every claim it makes carries a citation back to the item or recipe it came from. That's not a nicety: a model asked about this game will confidently produce a decade-old answer if you let it, so the citation is how a player tells a grounded answer from a remembered one.

Calendar & signups

Tenant-scoped

The calendar's hard problem isn't layout, it's time. Guilds are international, so every displayed time is labelled with the zone it's in — the tenant's by default, the viewer's on hover. An unlabelled raid time is this screen's characteristic bug, and it doesn't throw, it just assembles the wrong people at the wrong hour.

Notifications

In-app + Discord + push

The in-app centre is the system of record — every notification exists here whether or not it also reached Discord. Delivery status is shown per channel, because "did the guild actually get told" is the question people ask when something goes wrong, and a silently dead webhook is the most common way this feature fails.

Angular component map

Build order

Build the shared primitives first — every screen depends on them, and an item cell re-invented per feature is how a design system dies in week three.

Shared — src/web/src/app/shared/

  • <scribe-item-cell>Icon, name, sub-line, item level. Renders the Wowhead anchor. Inputs: item, showSlot, flagged.
  • <scribe-stat-tile>Label, value, sub-line. Tabular figures.
  • <scribe-status-pill>Dot + word. Inputs: state (ok | attention | critical | neutral), label.
  • <scribe-filter-chip>Key, value, remove. Emits removed.
  • <scribe-meter>Progress bar for raid and profession rows.
  • <scribe-empty-state>Heading, body, one action. Variant: error.
  • <scribe-skeleton>Shape-matched placeholder. Inputs: height, count.
  • <scribe-ai-badge>The generated-content marker. Never optional on AI output.
  • <scribe-tenant-switcher>Active community + the viewer's role. Switching navigates; it never mutates hidden state.
  • <scribe-rank-pill>A tenant rank. Colour comes from the tenant's own config as --rank-color, not from a token.
  • <scribe-signup-chip>Accepted / Tentative / Declined / Benched / No reply.
  • <scribe-local-time>Renders an instant in the tenant zone with the viewer's zone on hover. Both always labelled.

10

Non-negotiables

Carried from CLAUDE.md

If a change to the UI would break one of these, the change is wrong. Each is drawn somewhere on this page so it can be copied rather than remembered.

  • Tenant is visibleThe switcher shows the active community and the viewer's role on every tenant route. Acting in the wrong guild is the failure this prevents.
  • Tenant lives in the route/t/:tenantSlug/... — services build URLs from the active route, never a stored variable that can drift.
  • 404 means "not yours"Route to the picker. The UI never distinguishes "doesn't exist" from "not a member", because the API deliberately doesn't.
  • Times are labelledTenant zone by default, viewer's on hover, both named. An unlabelled raid time is a real bug, not a nit.
  • Delivery status is shownPer-channel, including failures. A silently dead webhook is how this feature fails in practice.
  • Webhook URLs are maskedNever rendered in full, never logged. It is a credential.
  • AttributionEvery page footer names Blizzard as the data source and disclaims affiliation. Blizzard ToU.
  • No trademarkThe product name is AegisScribe. No Blizzard mark in the title, the wordmark, or a URL.
  • Wowhead is client-sideItem cells render outbound anchors; the tooltip script decorates them. The server never calls Wowhead.
  • renameLinks: falseIn the tooltip config, or the script overwrites our item names and breaks anything matching on them.
  • AI is labelledEvery model-authored surface carries the generated badge. Streaming views carry a stop control.
  • Filters are visibleNatural-language results always show the interpreted filter as removable chips.
  • Staleness is visibleA character page states when it was last synced. Degraded reads say how old they are.
  • State is never colour alonePills pair a dot with a word. Quality pairs a border with a name.
  • Roles hide, servers enforceRole-conditional UI is cosmetic. Every protected view has a server policy behind it.
